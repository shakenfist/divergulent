# Deterministic marking of generated build-system output

Some carried patches are dominated by the output of a build- or
configuration-system generator — an autotools regeneration committed
into an old-style `1.0` source diff. The motivating case is the
`gatos` source patch (`gatos_0.0.5-19.2.diff`, fingerprint
`c1ed3922…`): 1.7 MB, 54,465 lines, of which ~98% of changed lines
land in ten classic autotools output files (`configure` alone is
19,258 changed lines; `ltmain.sh`, `libtool.m4`, `aclocal.m4`,
`config.guess`/`config.sub`, `config.h.in`, `missing`, and eleven
`Makefile.in`s make up the rest). The hand-written residue is ~800
diff lines across 15 files — entirely reviewable, but buried.

Today that patch is a dead end in the pipeline: the reviewability
axis calls it `oversized`, so LLM triage skips it and routes it to a
human; the risk gate scored `elevated` off a 40k-char head that was
almost entirely `configure` noise; the dangerous-construct scan
recorded 128 `shell-out` observations, all in generated shell; and it
sits in the review queue as `unknown` with no draft to assist the
reviewer.

This plan adds a **deterministic, per-file "claims to be generated"
mark** — an observation, never a verdict — and uses it to:

1. concentrate a human reviewer's attention on the hand-written
   residue (review UI badges, collapsed generated segments), and
2. un-strand these patches from the `oversized` dead end by giving
   the LLM passes a **residue-first projection** of the diff.

## Measured shape of the problem

From the reviews corpus (~60.6k distinct fingerprints), scanning the
939 fingerprints currently observed `large` or `oversized`:

- **33** have ≥90% of changed lines in generated-named files, and
  **6** more have 50–90% — so ~39 patches carry a dominant generated
  component, about a quarter of the 151-patch `oversized` bucket.
- **38** more have a minor (<50%) generated component; **862** have
  none.
- Generator **banners** ("Generated by GNU Autoconf 2.59",
  "generated by automake 1.9.6") appear in only 38 of the 939 bodies
  — a banner is only visible when a hunk happens to touch the top of
  the file — so the **filename signal must lead** and the banner
  signal corroborates.

The population is small and shrinking (modern `3.0 (quilt)` packages
regenerate at build time via `dh_autoreconf` and never carry this
output), but it is concentrated in exactly the bucket that today has
no good story.

## Posture: a mark, never a verdict

The project has (correctly) never been comfortable with a rule that
*categorises* automated build output, and this plan does not add one.
The xz-utils backdoor shipped precisely in dist-only generated build
machinery, exploiting the reviewer reflex that autoconf output is
unreviewable noise. So:

- The mark asserts only the checkable claim: "this file *claims* to
  be generator output" (by name, and where visible, by banner). It
  never asserts the content is benign, and it never settles a
  category.
- The generated bulk stays in the record and stays visible — badged
  and collapsed, not hidden or dropped. A reviewer can always expand
  it.
- Upgrading "claims generated" to "verified generated" (rebuilding
  the autotools output in a pinned-era container and subtracting it)
  is explicitly **out of scope** here and captured under Future
  work.

This mirrors the posture of the dangerous-construct scan and the
injection tripwire: a flag with evidence, consumed by routing and
display, supersedable, versioned.

## Design decisions

### A new scanner module, not a file-typing change

`content._classify_file` already types `configure` / `Makefile.in`
as `build`, but that axis conflates hand-written build inputs
(`configure.ac`, `Makefile.am`) with generated outputs (`configure`,
`Makefile.in`) — and downstream rules depend on the current typing.
Generated-ness is an **orthogonal axis** (hand-written vs generated,
not build vs code), so it lives in a new module,
`divergulent/classify/generated.py`, mirroring `injection.py`'s
shape: pure functions over the patch body, no I/O, reusing
`content`'s section parser so path handling matches `profile()`
exactly.

Two signals per touched file, recorded separately in evidence:

- **`name`** — the basename/path matches the well-known autotools
  output set: `configure`, `Makefile.in` / `GNUmakefile.in`,
  `aclocal.m4`, `acinclude.m4`, `ltmain.sh`, `libtool.m4`,
  `ltoptions.m4` / `ltsugar.m4` / `ltversion.m4` / `lt~obsolete.m4`,
  `config.guess`, `config.sub`, `config.h.in`, `missing`,
  `install-sh`, `depcomp`, `compile`, `ylwrap`, `mkinstalldirs`,
  `config.status`, `configure.lineno`, `texinfo.tex`. (Exact set to
  be settled by the phase-1 corpus measurement; extensible to other
  generator families later — gettext's `po/Makefile.in.in` machinery,
  cmake output, generated protobuf — each as a named family like the
  injection tripwire's pattern families.)
- **`banner`** — a generator self-identification visible in the
  file's hunks (added, removed, or context lines): "Generated by GNU
  Autoconf", "generated by automake", "generated automatically by
  aclocal", "GNU Libtool", `@generated`. The matched generator
  version string is captured as evidence — it dates the regeneration
  (gatos: autoconf 2.59 / automake 1.9.6 / one aclocal 1.4 banner, a
  mixed-toolchain fossil record), which the Future-work verification
  idea needs.

### One observation per patch, per-file detail in evidence

Kind (working name) `generated-content`, `observed_by =
'generated-scan'`, `rule_version = GENERATED_RULES_VERSION`. One
observation per fingerprint (like `reviewability`, unlike the
per-hit dangerous-construct rows — 21 touched generated files should
not be 21 rows). `detail` carries the family and a coarse coverage
figure (e.g. `autotools/98%`); `evidence` is canonical JSON with the
per-file breakdown: path, signals fired (`name`, `banner`,
generator version if seen), added/removed counts, plus the patch
totals and the **residue changed-line count** (changed lines in
non-generated files) that routing consumes. Stable per fingerprint,
so the recorder can skip unchanged re-records; bumping the version
supersedes and re-scans exactly like every other deterministic rule.

### The residue unlock: triage and risk read hand-written lines first

- **Reviewability stays honest.** The size axis keeps measuring the
  total diff — a 47k-line patch *is* oversized as a structural fact.
  No change to `reviewability.py` levels.
- **Triage routing consults both.** Where the driver currently skips
  every `oversized` fingerprint, it will skip only those whose
  *residue* is also over the threshold: an `oversized` patch whose
  residue changed-line count is within triage range becomes
  triageable. gatos (residue ~800 lines) lands in `large` territory
  and gets a real LLM draft instead of `unknown`.
- **Residue-first projection.** For any patch with a live
  `generated-content` observation, the diff text fed to triage and
  to the risk gate is reordered: non-generated file segments first
  and whole, then a one-line explicit note per omitted/deferred
  generated segment ("`configure`: 19,258 changed lines, marked
  generated (name+banner), not shown"). The projection is loud,
  never silent — the model is told what it is not seeing, and the
  truncation flag is recorded as it is today. This fixes the risk
  gate's current failure mode, where `RISK_MAX_DIFF_CHARS` reads 40k
  chars of `configure` head and the actual code changes never enter
  the window.
- The injection tripwire runs over the **full** body, unchanged —
  it is cheap, and generated segments are exactly where hidden text
  would hide.

### Review UI: badge and collapse, never hide

- The CLI review view's files-changed summary (`FileStat` /
  `_format_file_list`) marks generated files (e.g. a `[gen]` tag),
  so the reviewer sees at a glance that the bulk is claimed
  machinery and where the hand-edits are.
- The web UI badges the same files in the files-changed list and
  renders generated file segments **collapsed by default**
  (expandable), with the worklist and detail page carrying a badge
  like the injection one ("mostly generated: autotools, 98%").
- The queue-priority bands are untouched: a generated-heavy patch is
  neither promoted nor demoted by the mark; its priority continues
  to come from risk / injection / provenance / reach as today.

Phase 1 mirrors the injection tripwire's evaluation-first approach:
build the pure scanner, run it over the whole corpus (not just the
big patches), write down hit rates per signal and per family, and
adjudicate the surprises (hand-written files that match the name
set, generated files the set misses, `.ori`/`.orig` backup copies —
which are *not* generated and must not be marked) before anything
touches the ledger. Phases 2–4 are independent enough to land as
separate PRs; phase 3 is the one that changes LLM behaviour and
should be planned at high effort.

## Success criteria

* The scanner is pure (no I/O), versioned, and its full-corpus hit
  rates are measured and written down in a phase-1 findings
  document, with every surprising hit adjudicated.
* A `generated-content` observation (final name settled in phase 2)
  is recorded idempotently during the record pass, supersedes
  cleanly on version bump, and round-trips through export/import.
* An `oversized` patch whose residue is small gets an LLM triage
  draft and a risk score computed over the residue-first
  projection, with the omitted generated bulk explicitly noted in
  the prompt and the truncation recorded in evidence.
* The gatos patch specifically: leaves the `unknown` dead end,
  carries a draft category, and renders in the review UI with the
  ten generated files badged and collapsed and the ~800-line
  residue immediately visible.
* No category rule keys on the mark; grep-level check that nothing
  maps `generated-content` → a verdict.
* `docs/deterministic-rules.md` documents the rule (signals,
  precedence, measured hit rates); `ARCHITECTURE.md` gains the
  module; `pre-commit run --all-files` passes per phase.

## Out of scope / honest boundaries

- **Verification by regeneration** — building a pinned-era autotools
  container and subtracting the regenerated output from the diff.
  Deferred to Future work; the mark deliberately says "claims", not
  "is".
- **Any category verdict from the mark.** A patch that is 98%
  generated autotools output can still carry a backdoor in the
  other 2% — or in the generated 98%.
- **Client-side anything.** The scan, the observation, and the
  routing are curation-side; clients never run any of it. (Whether a
  *derived* signal should reach users is the separate cruftiness
  question under Future work.)
- **Non-autotools generator families** beyond a stub registry:
  measured first, added only when a real corpus population shows up.

## Open questions

- Final observation kind name (`generated-content` vs
  `generated-file` vs `generated-bulk`).
- Should phase 3 re-run the risk gate over the ~39 affected patches
  once the projection exists (their current `elevated` scores were
  computed from generated-noise heads), or wait for the next sweep?
  Re-running is cheap (n≈39) and the stale scores drive queue
  priority today — leaning yes, as part of phase 3's rollout.
- Coverage threshold, if any, for the *observation* itself: record
  the mark for any generated-file hit (even one file in a small
  patch), or only when generated lines dominate? Leaning: record
  always (the observation is cheap and honest), let consumers apply
  their own thresholds (the residue unlock naturally only matters
  when the residue is small).
- Whether the residue-first projection should also drop generated
  segments from the *dangerous-construct* scan's attribution or
  leave its 128 `shell-out` rows as-is (they are true statements
  about the diff, just noisy). Leaning: leave the scan alone, but
  have the review UI's badge note when all construct hits fall
  inside marked-generated files.

## Future work

- **Rebuild-and-subtract verification.** For the ~39
  generated-dominated patches: read the generator versions from the
  banners, build a matching-era toolchain container from
  snapshot.debian.org (no network at run time — autoreconf on
  attacker-influenced input is code execution), regenerate, and
  diff the regenerated files against the patched ones with
  normalisation (timestamps, serials). Byte-identity will be
  fragile (Debian-patched autotools, aclocal include paths, the
  mixed 1.4/1.9.6 toolchains visible in gatos), so the design must
  degrade gracefully: a partial match shrinks the residue-of-the-
  residue a human reviews; a total mismatch degrades to today's
  behaviour. Needs `.orig` tarball acquisition, which the corpus
  deliberately does not do today. A batch tool run once, emitting a
  `generated-verified` observation — not a pipeline tier.
- **User-facing "ancient and crufty" signal.** Graduated to its own
  master plan, [PLAN-maintenance-health.md](PLAN-maintenance-health.md),
  which splits it into a client-facing maintenance-health block and
  a curation-facing review-freshness ordering. This plan's
  generator-version stamps (autoconf 2.59 dates gatos's last real
  regeneration to ~2003–2006) are that plan's strongest input — the
  one fossil signal a rote packaging refresh cannot launder.
