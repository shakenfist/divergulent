# Generated-marking phase 1 — scanner + full-corpus measurement

Build the pure generated-output scanner and measure it against the whole
corpus **before** anything touches the ledger. This phase mirrors the
injection tripwire's evaluate-first shape: a versioned, pure scanner
module; a measurement tool run over all ~60.6k fingerprints; a findings
document that adjudicates every surprise; and a tuned v1 signal set. No
ledger writes, no routing changes, no UI — those are phases 2–4.

The scanner's job is one honest, checkable claim per touched file:
"this file *claims* to be build-system generator output", from two
independently-reported signals — its **name** and any generator
**banner** visible in its hunks. Phase 2 records the claim; phase 3
routes on it; nothing ever categorises on it.

## Evidence already in hand (master plan, 2026-07-25)

- gatos (`c1ed3922…`): 47k changed lines, ~98% in ten autotools output
  files, ~800-line hand-written residue.
- Of 939 `large`/`oversized` fingerprints: 33 are ≥90% generated-named
  lines, 6 more 50–90%, 38 minor, 862 none.
- Banners appear in only 38/939 bodies (a banner needs a hunk near the
  file top), so **name leads, banner corroborates** — but the banner
  signal must also run standalone, because a banner in a file the name
  set misses is exactly how the name set's gaps are found.

## Design decisions

### A pure scanner module mirroring `injection.py`

`divergulent/classify/generated.py`: pure functions over the patch
body, no I/O, reusing `content._parse_sections` so path handling,
header skipping, and per-file added/removed counts match `profile()`
exactly. Versioned as `GENERATED_RULES_VERSION = 1`; signal tables
live in one registry keyed by family (`autotools` only in v1, shaped
so gettext/cmake families can be added later without reshaping).

Public API (settled here so phase 2 can consume it unchanged):

- `scan(text) -> GeneratedScan` — frozen dataclass:
  `files: tuple[GeneratedFile, ...]` (only the *marked* files), plus
  `generated_changed`, `total_changed`, `residue_changed` (changed
  lines in unmarked files — what phase 3 routes on) and `coverage`
  (generated fraction, 0.0 when nothing matched).
- `GeneratedFile(path, family, signals, generator, version, added,
  removed)` — `signals ⊆ {'name', 'banner'}`; `generator`/`version`
  captured from the banner when present (e.g. `('autoconf', '2.59')`),
  else `None`. The version string is evidence the future
  rebuild-and-subtract work needs; capture it now.

### The name signal: exact basename, any depth, backup-suffix aware

Exact basename equality (never substring), matched at any path depth —
`m4/libtool.m4` and a subdirectory `configure` are as generated as
top-level ones. The v1 candidate set, to be confirmed or trimmed by
measurement:

`configure`, `Makefile.in`, `GNUmakefile.in`, `aclocal.m4`,
`libtool.m4`, `ltoptions.m4`, `ltsugar.m4`, `ltversion.m4`,
`lt~obsolete.m4`, `ltmain.sh`, `ltconfig`, `config.guess`,
`config.sub`, `config.h.in`, `config.status`, `configure.lineno`,
`missing`, `install-sh`, `mkinstalldirs`, `depcomp`, `compile`,
`ylwrap`, `ar-lib`, `py-compile`, `test-driver`, `mdate-sh`,
`texinfo.tex`.

**Backup suffixes are stripped before matching, not excluded.** A
`.ori`/`.orig`/`.bak`/`.rej`/trailing-`~` name is classified by what
it is a copy of: `Makefile.in.ori` → `Makefile.in` → marked;
`Makefile.am.ori` (the gatos case) → `Makefile.am` → not marked. This
keeps the claim honest in both directions.

**Deliberately absent: `acinclude.m4`.** By convention it is a
maintainer-*written* input (aclocal reads it), even though the common
historical practice of pasting `libtool.m4` into it means its content
is often machine-copied — gatos's 3,647-line `acinclude.m4` delta is
exactly that. It stays out of the name set; the banner signal may
still fire on its pasted content, and the measurement must report how
often that happens so the findings can settle it with data.

### The banner signal: standalone, version-capturing, whole-hunk

Patterns run over **all** of a file's hunk lines (added, removed, and
context — banners usually arrive as context), on every touched file,
not just name-matched ones. v1 patterns, each capturing a version
where the format carries one:

- `Generated by GNU Autoconf <v>` (autoconf)
- `generated by automake <v>` (automake)
- `generated automatically by aclocal <v>` (aclocal)
- `Generated from <file> by autoheader` (autoheader)
- `ltmain.sh (GNU libtool)` / `GNU Libtool` (libtool)
- `@generated` (the modern machine-readable convention)

A generic `DO NOT EDIT` family is measured as a **candidate only**
(reported separately, not marking) — too generic to trust unmeasured.
`timestamp='…'` lines in `config.guess`/`config.sub` are treated as
version evidence on name-matched files, never as a standalone banner.

### Measurement tool under `tools/generated-marking/`

Following the `tools/injection-screening/` precedent: a standalone,
offline script (`measure.py`) that walks a corpus (fingerprint index +
content-addressed bodies), runs `scan()` on each representative body,
and writes a machine-readable results file plus a human summary:

- per-name match counts, and what fraction of each name's matches
  carry a corroborating banner;
- banner hits on files **outside** the name set (the gap list), with
  counts per basename — name-set candidates for adjudication;
- patch coverage distribution (0 / <50% / 50–90% / ≥90%) over the
  whole corpus, and the ≥50% list with residue changed-line counts —
  phase 3's exact target population;
- every distinct matched path for low-frequency names (`compile`,
  `missing`, `ltconfig`, …) so false-positive candidates get eyeballed
  rather than assumed away;
- `acinclude.m4` banner-hit counts (the deliberate-absence check);
- runtime over the full corpus (expected trivial; it is regex + the
  existing section parser).

## Testing requirements

- Name matching proven at each edge: depth, backup-suffix both
  directions, substring non-matches (`preconfigure`, `reconfigure.ac`),
  case sensitivity (these names are case-sensitive on disk).
- Every banner pattern has a positive and a negative test, and version
  capture is asserted (`2.59`, `1.9.6`-style strings).
- The gatos-shaped fixture asserts the arithmetic phase 3 will rely
  on: `residue_changed + generated_changed == total_changed`.
- The measurement tool runs against a committed fixture corpus in
  tests; the real-corpus run is S3, never CI.
- `pre-commit run --all-files` green per step.

## Success criteria

- `scan()` is pure, versioned, and its full-corpus behaviour is
  measured and written down, with every low-frequency name hit and
  every name-set gap candidate adjudicated in the findings document.
- The ≥50%-coverage population and its residue sizes are enumerated —
  phase 3 starts from that table, not from estimates.
- The gatos fingerprint's scan output matches the hand analysis (ten
  generated files marked, `Makefile.am.ori` not marked, residue ≈800
  changed lines).
- Zero changes to ledger, routing, or UI; `content.py` untouched
  except (if unavoidable) a public re-export of the section parser.

## Open questions (to be answered by S3's data)

- Does `acinclude.m4` stay out of the name set once its banner-hit
  rate is known, or does pasted-libtool content justify a separate
  `copied-input` disposition?
- Do the short generic names (`compile`, `missing`) ever match
  non-autotools files in this corpus, or is exact-basename precise
  enough in practice?
- Does the `DO NOT EDIT` candidate family find enough real generated
  content (cmake, gettext, generated headers) to justify a second
  family in v1, or does it wait for a family of its own?
- Do `config.status` / `configure.lineno` ever actually appear in
  carried patches (they are build-time products, not dist products) —
  keep or drop from the set?

## Out of scope

- The ledger observation, its kind name, and the record pass — phase 2.
- Residue-first projection, the oversized unlock, risk re-scoring —
  phase 3.
- Review UI badges/collapse — phase 4.
- Non-autotools families beyond the measured `DO NOT EDIT` candidate.
- Rebuild-and-subtract verification (master plan Future work).

## Back brief

Before executing: this phase ships a **pure scanner and numbers** —
nothing observable changes for the pipeline or any user. The scanner's
claim is "this file says it is generated", reported per file with the
signal(s) and any generator version; the arithmetic it emits
(`residue_changed`) is what phase 3 will route on, so its correctness
is the point of the tests. Name leads, banner corroborates and finds
gaps; `acinclude.m4` is deliberately excluded pending data; backup
suffixes classify as what they copy. Measurement precedes belief.
